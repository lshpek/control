# Автоматический мониторинг сервисов и Telegram-оповещения

## Настройка

1. В локальном `.env` задай `TELEGRAM_BOT_TOKEN` — токен бота `@botvexdev_bot`. Не публикуй его и не вставляй в исходники.
2. Открой `@botvexdev_bot` в Telegram и нажми **Start** от имени аккаунта, который должен получать уведомления.
3. Укажи числовой ID аккаунта (или группы) в `TELEGRAM_ALERT_CHAT_ID`. Это ID получателя, а не `@botvexdev_bot`. Для группы бот должен быть добавлен в неё.
4. Оставь `SERVICE_MONITOR_ENABLED=true`; интервал цикла по умолчанию 30 секунд, таймаут HTTP-проверки — 5 секунд.
5. В разделе «Сервисы и боты» заполни `health_endpoint` либо `url`. Проверяются только активные сервисы с указанным URL. Интервал сервиса задаётся в `desired_check_interval_seconds` (минимум 60 секунд).
6. Перезапусти backend. В логах появится `Service monitor started`.

## Поведение

- Фоновый монитор выполняет HTTP(S)-проверки, не следует редиректам и отклоняет localhost, приватные и зарезервированные IP-адреса.
- Статус, источник `probe` и время последней проверки сохраняются в SQLite; смена состояния добавляется в журнал активности.
- Telegram-уведомления отправляются при переходе к `degraded`/`down` и при восстановлении из этих состояний. Неизменившийся сбой не вызывает сообщение на каждом цикле.
- `unknown → healthy` не отправляет уведомление о восстановлении, чтобы не создавать ложную тревогу после первой настройки.
- Если ID получателя или токен не задан, мониторинг продолжит обновлять статусы, но Telegram-уведомления не отправятся.
- Внутрипроцессный монитор рассчитан на один Uvicorn worker; при нескольких workers каждый процесс запустит свой цикл.
- Доставка ограничена несколькими попытками и не является устойчивой очередью. При недоступности Telegram сообщение может потеряться.

## Проверка

Из корня проекта:

```powershell
python -m pytest backend\tests -q
```

Для теста используй публичный endpoint, который ты контролируешь. Не добавляй чужие внутренние адреса, локальные IP или тестовые секреты в открытый репозиторий.
